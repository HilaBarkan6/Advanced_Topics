מחלקות ואובייקטים
כל אובייקט שתואר בהוראות המשחק, קיבל מחלקה בקוד כדי שהיה ישות עצמאית עם תכונות ופונקציות מתאימות עבורו
משחק מוגדר על ידי - לוח שהוא מטרציה של אובייקטי משחק
שני טנקים עם מזהה לפי שחקן
שני שחקנים
את כולם מחזיק מנהל המשחק כמשתני מחלקה והוא אחראי על הפעלתם ועל מהלך המשחק.
בנוסף, מתוקף כך, מנהל המשחק אחראי על בדיקת תקינות של כל המהלכים ושל כל מקרי הקצה שעלולים להיות במשחק, התהגותו תוכננה לתמוך במקרים סבירים כמו שראינו בפורום
את השחקנים תכננו כישות עצמאית מהמשחק ובמחשבה שקוד שחקן עשוי להצטרף גם בעתיד, מבלי לדעת כלום על המימוש הפנימי של המשחק
לכן תכננו את הקשר בין המשחק לשחקנים להיות רק מה שהכרחי - השחקן מקבל ממנהל המשחק את הלוח ומיקומי הטנקים (קונסט) ורק מחזיר פעולה שהוא רוצה לעשות
התקשורת בין השחקן למנהל המשחק היא בעזרת הEnum
השחקן בכוונה לא יכול לערוך כלום במצב המשחק ומקבל מידע כקונסט כדי שלא יוכל לממש כוונות זדוניות
בנוסף, לשחקן יש לוגיקות פנימיות שגם הוא לא חושף, ומציג למנהל המשחק רק החלטה סופית בצורת בקשה לפעולה

מהלך המשחק
על מנת לאפשר מהירות שונה לפגזים וטנקים, בחרנו לממש את לולאת המשחק לפי העצה שניתנה בפורום, הכפלת התורים וחלוקה לזוגיים ואי זוגיים
כך שבתור זוגי גם טנקים וגם פגזים זזים ובתור אי זוגי רק הפגזים.
בצורה כזאת כל תור משחק מורכב משתי איטרציות של הלולאה וכך מתקבלת ההתנהגות הרצויה

Design Considerations –
Classes and Objects
    Every object described in the game instructions received its own class in the code so that it would be an independent entity with appropriate properties and functions.

    A game is defined by:

     - A board, which is a matrix of game objects

     - Two tanks, each with an identifier according to the player

     - Two players

    All of these are held by the game manager as class variables, and it is responsible for their operation and for the flow of the game.
    Additionally, due to this structure and the given instructions in the assignment, the game manager is responsible for checking the validity of all moves and all edge cases that may occur in the game.
    Its behavior was designed to support reasonable scenarios, as discussed in the forum.

    We designed the players as independent entities from the game, under the assumption that player code may be added in the future without knowing anything about the internal implementation of the game.
    Therefore, we designed the connection between the game and the players to include only what is necessary – 
    the player receives from the game manager the board and the tank positions (as constant refrences) and only returns an action it wants to perform.
    Communication between the player and the game manager is done via a shared Enum called Action, which represents a wanted action from the player.

    The player is intentionally unable to modify the game state so it cannot carry out malicious intentions.
    Additionally, the player has internal logic that it also does not expose, and it only presents the game manager with a final decision in the form of an action request.

Game Flow
    In order to allow different speeds for shells and tanks, we chose to implement the game loop according to the advice given in the forum: 
    doubling the turns and dividing them into even and odd turns.
    In this way, during even turns, both tanks and shells move, and in odd turns, only the shells move.
    In each type of iteration (even or odd) the possible objects collisions are checked and handled appropriatly.
    Thus, each game turn consists of two iterations of the loop, resulting in the desired behavior.
